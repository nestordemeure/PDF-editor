# CLAUDE.md

In-browser PDF cleanup tool for scanned books. Vanilla JS ES modules, no build step for the page: serve the directory statically (`./serve.sh`) and open `index.html`. PDF.js, Sortable and tesseract.js come from CDNs.

The engine is the desktop app's Rust code (`desktop/`), compiled to WebAssembly. The build output in `src/engine/` is committed, so GitHub Pages serves it as is. After a change to the Rust code, run `desktop/web/build.sh` and commit `src/engine/`.

## Code organization

App code lives in `src/`; `index.html`, `style.css`, and `serve.sh` stay at the root (GitHub Pages serves the repo root). `test data/` holds sample PDFs (not in git).

| File | Role |
|---|---|
| `src/app.js` | Entry point: UI wiring, app state (`pages`, `sourcePdfs`), undo/redo history, page grid, load/save handlers |
| `src/pageModel.js` | Page objects and their operation list (`rotate`, `split`, `colorMode`, `removeShading`, `enhanceContrast`) |
| `src/pageCommands.js` | Commands that edit operation lists and update thumbnails; `forEachConcurrent` |
| `src/pageRenderer.js` | PDF.js renders: base-thumbnail cache, thumbnails through the engine preview, full renders for the engine |
| `src/engine.js` | Engine access: the Library worker, the pixel worker pool, `previewPage` |
| `src/engineWorker.js` | Module worker holding the engine's `Library`: sources, save plan, output writer |
| `src/pixelWorker.js` | Module worker running page and image jobs |
| `src/ocr.js` | tesseract.js workers; returns lines in the engine's format |
| `src/saveManager.js` | Save orchestration between the workers |
| `src/engine/` | Generated by `desktop/web/build.sh`; do not edit |
| `desktop/web/` | Rust crate that exposes the engine to JavaScript (`wasm-bindgen`) |

## Architecture

Editing is **non-destructive**: pages store a source reference plus an operation list. The engine turns a page's operations into its own page model (`to_page` in `desktop/web/src/lib.rs`): rotations and splits fold into a view (crop and quarter turns), and the last color mode applies. Everything the desktop documents about routes, pixel operations and output (`desktop/CLAUDE.md`) applies here.

- **Load**: the Library worker reads each file (decryption with the empty password, page classification, text stripping). PDF.js gets the same file, or the engine's rewrite after stripping.
- **Thumbnails**: PDF.js renders the source page at 300 px wide; the engine's `preview` applies the view and pixel operations. This is the save's code, so the preview matches the output.
- **Save**: the Library worker plans the save and gives one job per page, with the source data it needs. Pixel workers run the jobs. Pages without a decodable scan image get a PDF.js render first. With OCR, tesseract.js reads the image the job returns, and the Library worker writes the text layer. Each finished page goes to the output at once; the output reaches the main thread in chunks, which become a `Blob`.

## Invariants — breaking these causes subtle bugs

- **Thumbnail canvases are replaced, never mutated in place.** Undo history snapshots and the page-grid card cache hold them by reference.
- The base-thumbnail cache (`baseThumbnailCache`) must hold the **pre-operation** render; it is what lets pixel-effect changes and deep undo skip PDF.js entirely.
- **Call `page.cleanup()` after each PDF.js render.** PDF.js otherwise keeps every decoded scan image: about 30 MB per page of a book.
- **Split regenerates thumbnails.** Contrast and adaptive B&W depend on what the crop keeps; only rotation can reuse the thumbnail.
- **Pages in flight are bounded** (`forEachConcurrent` in `saveManager.js`). Never collect page results before writing them.
- **Fail loudly.** A failed worker, job or OCR load stops the save with its error; there are no silent fallbacks.
- The wasm-bindgen crate version in `desktop/web/Cargo.toml` must equal the `wasm-bindgen` command-line tool's version.
- `desktop/web/build.sh` patches jbig2enc-rust (`jbig2enc-web-time.patch`): it times its work with `std::time::Instant`, which panics in browsers.

## Development priorities

1. **Correctness**: preview must match output; never silently degrade image quality or grow file size — verify sizes stay equal-or-smaller on the test files.
2. **Output size**: small gains are worth pursuing — books are hundreds of pages, each an image.
3. **Responsiveness**: the UI must stay live during long operations (workers, throttled yields, progress in the status bar). Whole-book interactive operations should stay in low seconds.
4. **Memory**: the tab's memory must not grow with the book. Watch it in benchmarks (see below).

## Testing

No test suite for the page; verify end-to-end headlessly: install `playwright` in a scratch dir (`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`, launch with `channel: 'chrome'`), serve the app with `python3 -m http.server`, upload a test file via `#fileInput`, drive the buttons, and capture the download. Validate outputs with `qpdf --check`, `pdfimages -list`, `pdftoppm` (visual), `pdftotext -bbox` (OCR alignment), and `pdffonts` for text pages. The desktop CLI (`pdf-editor-cli`) gives reference outputs: web outputs should match its sizes closely (page write order and PDF.js renders differ).

Benchmark with `test data/book66.pdf` (66 pages). Run the browser under a memory limit that kills it (sum the RSS of the `playwright_chromiumdev` processes): this machine has 16 GB, and a 330-page book has filled the swap. Ask before a run larger than 66 pages.

Test files are listed in `desktop/CLAUDE.md`.
